# Review, 2026-08-23

Two independent review agents went over the initial implementation (`19b568c..53e2899`):
an adversarial code review against the PF2e system's own flanking implementation, and an API
audit checking every Foundry/PF2e call against the v14 API docs and PF2e 8.4.1 source.

This file records what they found, what was done about it, and what is deliberately left.

## Verdict

**Every Foundry and PF2e API the module calls is correct** - 28 checked, none wrong. That
covers the ones that could not be tested locally: `isPreview`, `_original`,
`canvas.tokens.preview.children`, `polygonBackends.move.testCollision`, all hook names, both
`register` signatures, and the PIXI surface (v14 still ships PIXI 7, so `lineStyle`/`beginFill`
are current, and Foundry swaps in `SmoothGraphics`, which supports them all).

The real defects were in the rules, not the plumbing.

## Fixed

### 1. Reach was measured with Chebyshev distance (rules bug)

`squareGap` counted every diagonal as one square. PF2e alternates diagonals 5/10, so two
diagonal steps are 15 feet, not 10. Correct at 5 and 10 feet by coincidence; wrong from 15 up -
reach weapon plus Lunge, or any Large creature with reach.

The system measures square grids with its own `measureDistanceCuboid` → `measureDistanceOnGrid`
(`src/module/canvas/helpers.ts`), *not* `canvas.grid.measurePath` - that is only its
non-square-grid path. `src/distance.ts` is a port of that function:
`floor(doubleDiagonal * 1.75 + diagonal * 1.5 + straight)`, including the CRB p.455 carve-out
that lets a 10-foot reach cover two diagonal squares. Reach is now compared in feet against
`getReach()` rather than being rounded into squares.

### 2. Elevation was ignored

A flyer 20 feet overhead counted as flanked by two melee tokens on the ground. Elevation is now
the third axis of the same measurement, using each creature's vertical span
(`document.elevation` plus `actor.dimensions.height`), as PF2e does.

### 3. Hidden and unseen tokens

PF2e's `canFlank` refuses when either token is GM-hidden, *for everyone including the GM*; the
module allowed it, so a GM saw flanks the system would not back with off-guard. Worse, the token
filter never consulted `token.visible`, so a player could see outlines and connector lines on
tokens their character cannot perceive - a position leak. Both fixed: hidden tokens are out for
everyone, and non-GM clients only reason about tokens they can see.

### 4. Non-square grids drew confident nonsense

Hex and gridless scenes went through square-grid geometry: wrong distances, outlines that do not
line up with the tokens. `render()` now bails on any non-square grid and warns once per scene.

### 5. `refreshToken` recomputed everything every animation frame

The hook fires per frame per token, and `render()` is O(tokens²) with no caching - a plausible
way to wedge a browser on a busy scene. It is only load-bearing for the drag preview, so it is
now gated on a preview clone actually existing.

The first cut of that gate was too tight, and dropping a token left its overlay on the square it
came from. A hook trace in v14 shows why: `updateToken` and `moveToken` both fire while the clone
is still alive, so the render they schedule still treats the clone as the token, and the frames
that follow are all `refreshToken` with an empty preview - exactly what the gate discards. The
gate now also lets through the one frame where the clone goes away.

### 5b. A drop left the overlay on the square the token came from

Three fixes deep before a console trace found it, and the first two were aimed at the wrong
half. What the trace showed: `updateToken` and `moveToken` both fire while the drag clone is
still alive, and `requestRender` was *discarding* requests that arrived during a pending frame
rather than collapsing them - so the one draw that ran was the stale one. Both are fixed, and
both were real. Neither was the cause.

The cause was reading a position that is still moving. Foundry v14 animates `document.x/y`
themselves - the trace caught a draw at `4050,1668.72`, eighteen pixels into a 450-pixel slide -
so every draw a drop schedules reads a point partway along the path and floors to the square the
token came from. `getOccupiedGridSpaceOffsets()` had the same problem and was dropped on the way
past; it is not in `@dfreds/foundry-types` at all, having been declared by hand off the back of
the API audit, which is exactly the kind of claim the audit could not check.

`TokenDocument#movement` carries the answer in `destination`, correct from the first frame. Two
things the trace had to settle, neither guessable: the movement reports `completed` for the whole
animation, so its `state` cannot tell a moving token from a still one; and a drag clone is the
mirror image, its `x`/`y` following the cursor while its `movement` still describes whatever the
real token did last. So the clone decides which source wins - `isPreview` takes the document,
everything else takes the destination.

Lesson for the next canvas bug: trace it before theorising. `CONFIG.pf2eFlankVision.debug = true`
prints every render request, frame and draw with what it saw.

### 6. The overlay could brick itself permanently

`clearOverlay()` did not check `destroyed` before calling `clear()`, and it is the first
statement in `render()`. Foundry's `SmoothGraphics#clear()` throws on a destroyed instance, so a
single teardown race meant every later frame threw in the same place and the module never drew
again - hidden by the `try/catch` as a console spam loop. Both `clear` and `destroy` are guarded.

### 7. Gang Up (withdrawn)

This review first claimed PF2e grants the flank to *both* parties when one has Gang Up, and the
module was changed to match. That was wrong. The feat reads "any enemy **you're** adjacent to is
off-guard as long as it's within reach of at least one of your allies" - only the creature with
the feat benefits, which is also what the system's own `isFlankingWith` checks. The change was
reverted; `gangsUp` reads the attacker's `canGangUp` and nothing else, and a test pins it.

### 8. `flankedBy` re-implemented the rules

It duplicated the opposite-sides test and bolted on a separate ad-hoc Gang Up path that emitted
at most one pair with an arbitrary buddy, so the two entry points could disagree. It now goes
through `buddiesFlanking` like everything else.

### 9. Housekeeping

- `pnpm typecheck` was failing at HEAD (test stub inference). Now clean, with
  `noUncheckedIndexedAccess` and `noImplicitOverride` on top of `strict`.
- No `any` and no type assertions anywhere: Foundry types come from `@dfreds/foundry-types`
  (the PF2e system's own hand-maintained definitions, versioned to Foundry builds), and
  `isFlankToken` is the single runtime-checked boundary between Foundry's types and PF2e's.
- `createActiveEffect` / `deleteActiveEffect` were dead hooks - PF2e v8 does not persist
  ActiveEffects, it builds them from items - and `canvasTearDown` was registered twice.
  Wall hooks were missing, so `wallsBlock` never refreshed on wall edits.
- `canAttack` was only rejected when explicitly `false`; PF2e requires it truthy.

## Verified in play, not by tests

The drag preview works: `refreshToken` does fire for drag clones, `_original` resolves, and the
prospective-position recompute renders correctly, including the placement dots. Confirmed by
video capture on the live server, v14 / PF2e v8.

## Deliberately not done

- **`game.pf2e.settings.automation.flanking` is not consulted.** With flanking automation off,
  the system applies no off-guard but this module still shows the flank. That is the point: the
  overlay answers "are you flanking" as a rules question, not "will the system apply a condition".
- **Side by Side (animal companion) and eidolon Gang Up variants.** `canGangUp` can hold
  `"animal-companion"` or `"eidolon"`; only the numeric and `true` forms are handled.
- **Placement dots ignore terrain and movement cost.** They answer "could I flank from there",
  not "can I get there this turn".
- **Grid pixel conversion still multiplies by `canvas.grid.size`** rather than going through
  `canvas.grid.getTopLeftPoint`. Equivalent on square grids, and non-square grids now bail
  early, so this is cosmetic until someone wants hex support.

## Still open

- **Test coverage gaps**: `wallsBlock` is never exercised (and the flanking test file stubs no
  `CONFIG`, so the first test to enable it would throw in `wallBetween`); `flankedTokens` has no
  tests; no test asserts a placement square is rejected for falling outside `sceneRect`;
  `surroundingSquares` asserts only on length, so a wrong-but-right-sized result would pass.
- **No caching in `render()`.** Every draw re-derives occupied squares for every token,
  O(tokens²) pairs. Gating `refreshToken` took the pressure off, but a memo per render is the
  real fix if a crowded scene ever stutters.
- **Multi-token drags** preview only the first dragged token.

## Proposal: drop the Alt+F keybinding

Removed for now, rather than kept on a guess.

The reasoning: the module has a master `enabled` setting in the client settings panel, and
individual toggles for each overlay. A hotkey is only worth its cost if the overlay is something
you turn on and off *mid-combat*, several times a session. That is an open question - and there
is a specific reason to doubt Alt+F in particular: core Foundry binds bare Alt to
highlight-objects, so Alt+F would also flash the object highlight overlay every time.

So: play a few sessions without it. If reaching for the settings panel to silence the overlay
becomes an annoyance, add the binding back with a chord that does not collide with Alt - and at
that point we will know which specific toggle it should hit (probably `enabled`, possibly
`placementDots`, which is the noisy one).

Removing it now also keeps the first public release from claiming a keybinding a user might want
for something else.
